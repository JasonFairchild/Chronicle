# Cleanup after simplifying

Status: planned 2026-11-07. Commits 1–4 done; commit 5 written, not yet committed.

## Context

A sweep after the simplify work turned up a handful of changes too small for a plan each but too many for one commit. Five of them are left, each its own commit; reviewing the fifth added three more: other source only tests call, node specs on the Dexie adapters, and contract suites kept only where a second backend is planned. The More menu's removal and the doc fixes from that sweep land before this plan. Deleted when done; anything lasting goes into the docs in the commit that makes it.

## Decisions

- **One change type from editor to store.** `EditorChange` (`DocumentEditor.vue`) and `DraftChange` (`draftsStore.ts`) became the same shape once the editor stopped emitting anchor ids and the title. One `DraftChange` in `types/draft.ts`, since it crosses a component, a composable and a store (CLAUDE.md, "Types live by who uses them") and is the working stage in ARCHITECTURE.md's table. The editor's comment on why its signals are required moves with it.
- **`baseContent` takes a string only.** `EntryDocument` was accepted for AnchorMenu's specs alone (TESTING.md: never loosen a source type for a test).
- **While composing, the page's `<h1>` names the task.** "Revise entry" and "Create related entry", the buttons that open them, as New entry's page already does. Reading keeps the entry's heading. This removes the title shown twice in both modes: the Title field is a revision's only title, and the related-entry page's left column is the only place the parent's is shown.
  - Left column: This entry, the parent's heading (its title, or its dateline muted when untitled, as the reading header does), its meta line, its editor, then the instructions, with the right column's "Marking a passage is optional" folded in. Right column: The related entry, then EntryComposer. Each column's label, heading and editor then line up.
  - The view passes the parent's heading and meta line in as props, from the computeds it already has. `session.parentTitle` goes: it was the title when the session began and was never refreshed on returning to the tab, so it could disagree with the meta line beside it.
  - The ids become `useId()`, as EntryComposer's are.
- **One anchor index per document, before Track B reviews the editor.** CHRONICLE_PLAN.md decided it as §5.4's first step; nothing waits on §5.4, and Track B unit 2 should review the final shape. Today a caret move in anchor mode walks the document about six times (the decorations, AnchorMenu's `caretAnchor` and `shouldShow`, each through `anchorSpans` and `anchorPieces`).
  - `anchorIndex(doc)` in its own module, `editor/anchorIndex.ts`: each anchor by id, in document order of its first piece (`ownAnchorAt` relies on it where two touch), with its outer span, kind, and passage and wording pieces, each piece keeping its mark instance for `removeMark`. An id that isn't a non-empty string is skipped, `anchorSpans`'s rule (`anchorPieces` turned it into `"null"`).
  - Memoized in a `WeakMap` keyed by the document: ProseMirror documents are immutable, so it's one walk per new document and none per caret move.
  - It replaces `anchorSpans`, `anchorPieces` and `piecesOf` in the commands, the decorations and the guard. The guard's outcome check, a slice per sealed anchor, is unchanged.
  - `AnchorRange` leaves the domain, and `anchorRangeOverlapping` is inlined into `markAnchor`, its one caller. Its touching-edge case gets an editor-level test, which nothing has today.
  - Left alone: `markTyped` (it reads only beside the typed range), `markFrames`'s `visibleIn`, the domain's JSON walks, and DocumentEditor's `collectAnchors` for the parked raised-wording mode.
  - Rejected, carried over from CHRONICLE_PLAN.md: a `DecorationSet` of sealed anchors mapped through each change, which sees text move but not marks added. Further, only if a profile shows it: an index per top-level block.
- **Orphaned anchors go, ahead of CHRONICLE_PLAN.md item 3.** The lock keeps every sealed anchor in its parent's document, and a related entry is sealed after its anchor revision in one `createMany`, so no version viewed lacks an anchor a visible related entry names. The orphan path and the quote saved for it are dead.
  - `AnchorRef` goes: a related entry stores `anchor_ids: string[]`. Connections folded may need each to name the entry whose document it marks, but nothing old is kept compatible, so item 3 settles that shape when it needs one.
  - `resolveAnchors` and `placedAnchors` go. The fold, the one reader left, reads the viewed version's anchors once and looks each id up, skipping any it lacks. `ResolvedAnchor` and `AnchorStatus` go; `DocumentAnchor` moves to `types/entry.ts`, since it now crosses from the domain to the page, and its `quote` and `insertion` become `passage` and `wording`, the docs' own terms (`quote` echoed the retired stored quote).
  - `anchorRefsFor` goes too: its ids come from `anchorsPlacedSince`, read off the same document, so with the quote gone its filter had nothing left to do. `anchorsPlacedSince` returns the anchors rather than their ids, so `relationTypeForAnchors` judges them without reading the document again, and the store maps them to ids.
  - Also gone: `describeAnchor`'s orphan lines and the page's italic for them.
- **Specs seed through `createMany`; `create`, `listChildren` and `listConnectionsFor` leave the repository.** App source calls none of them (TESTING.md, "Test the code the app runs").
  - `seedEntry` in `src/testing/`, taking what `createEntryInput` takes, and an optional repository for the contract suites and the Dexie spec. A batch can't refer to its own members' ids, so a tree is still seeded one entry at a time.
  - The contract suite's create cases (round trip, stored copy, every validation case) move onto `createMany`, which gains direct contract coverage it lacked. The `listChildren` and `listConnectionsFor` cases go: revisions left out of related entries and connections from either end are asserted at the fold (`reconstructEntryState.test`), and incoming connections by the `listDescendants` case.
  - Read-backs move to `listDescendants`, filtered, or `getById`. NewConnectionView's specs are updated too, though connections folded (CHRONICLE_PLAN.md item 3) removes them later.
- **Other source only tests call goes too**, by the same rule.
  - `buildEntryHistory`: each of its cases has a twin on `reconstructEntryState`, which the app calls. The one that hasn't, an update never counting as a version, moves onto "never lets an update replace the parent's content" as a `version.total` of 1. `historyFor`'s missing-entry and too-late guards were reached only through it, since `aggregate` checks both first, so they go: `historyFor` takes the `Entry` and returns `EntryVersion[]`, and `aggregate`'s null check on it goes too.
  - `MediaRepository.list` and `delete`: the app has never called either. Their one use would be reclaiming images no saved version references, ones attached in a draft that was discarded or removed before sealing. An image a saved version carries is history and is never deleted. Reclaiming needs both, so it becomes an engineering maybe in CHRONICLE_PLAN.md, and they return with it.
  - The writer's idea of an image attached to the entry as a whole, outside its text, apart from its versions or as a version of its own, becomes a maybe in PRODUCT.md §6.
  - Left for the history view: `MarkSetRepository.get` and `documentsFromFrames`, which CHRONICLE_PLAN.md's filter presets remove anyway.
- **Node specs run the Dexie adapters on `fake-indexeddb`; all four in-memory adapters go.** They were fakes kept honest by the contracts, and three node specs ran on them: entriesStore, draftsStore and markSetsStore (useSealDraft only fabricates one entry). Every repository change was written twice, and the in-memory draft adapter isn't transactional, so draftsStore's races ran against a different concurrency model than the app's. `fake-indexeddb` is IndexedDB for node, tested against the W3C suite and Dexie's own, so the specs run the code the app runs. The interfaces and the composition root stay: they are what makes SQLite a swap. Spiked: all three store specs pass, 54 tests, with the changes below. `InMemoryMediaRepository` goes in the same commit, so the docs saying every repository has an in-memory twin change once: no node spec stores media, and media code needs a browser anyway (blobs, object URLs, `<img>`).
  - `src/testing/nodeSetup.ts`, the unit project's one `setupFiles` entry, as `browserSetup.ts` is the browser's. Its first line imports `fake-indexeddb/auto`: Dexie reads the global `indexedDB` when its module loads, so the import must come before `realRepositories`, and inside the file the order can't be got wrong. Fresh entry, draft and mark-set repositories per test, disposed after; without disposal the spike's tests shared one database. Not media: `freshMediaRepository`'s disposer needs OPFS. Nothing is settled before disposal, since node specs don't track store actions; each spec already awaits what it starts.
  - The unit project's fake timers leave `setImmediate` real (`fakeTimers.toFake` in `vitest.config.ts`): fake-indexeddb schedules on it, and faking it hangs every write. `traceRecorder.test` already names its own.
  - A write a fake timer starts is still in flight when the advance returns, so three draftsStore tests await the spied `save` before reading back: TESTING.md's "wait on a signal the code already gives". The lost-write race test's delayed `getById` goes: real IndexedDB already yields, and without the delay the test still fails when `write`'s replaced-session check is removed.
  - What the in-memory adapters alone needed goes with them. `RelationLookups` drops its synchronous arms, and `entryValidation.test`'s lookups become async, rather than keeping a source type loose for a test. The entry contract's "stores a copy" case mutates after the write has landed, which IndexedDB's own clone already survives, so it proves nothing on Dexie and goes; no caller mutates an input it has handed over. The draft contract's "does not keep the caller's object" is rewritten to mutate before `save` resolves, the window `DexieDraftRepository.save`'s clone exists for, since the store's draft does change under a flush; seen failing without the clone, or dropped if no field reaches the stored row.
  - Rejected: the specs in browser mode, which needs no dependency but breaks TESTING.md's node placement for what isn't a component, and runs slower. Mocking the repositories, which would script the very conflicts the draft specs prove.
- **A contract suite is kept for an interface a second backend is planned for: entries and drafts**, the SQLite adapter's acceptance test (CHRONICLE_PLAN.md). Each runs once, in the browser, against Dexie; not in node too, which would prove fake-indexeddb rather than the adapter. Media plans no second backend, and the filter presets remove mark sets, so their contracts fold into `opfsMediaRepository.browser.test.ts` and `dexieMarkSetRepository.browser.test.ts` as plain `describe`s. The MIME helpers, shared in `mediaRepository.ts` for two adapters, move into `opfsMediaRepository.ts`.
