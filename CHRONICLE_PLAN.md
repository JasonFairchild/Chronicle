# Chronicle — Plan

What comes next, and the engineering work that is decided but not built. What decided features do for the user is [PRODUCT.md](./PRODUCT.md) §5; this doc holds the order and the technical side.

## Priorities

In order. Reorder here as priorities shift.

1. **Review:** working to understand and own existing code, in the order [CODE_REVIEW.md](./CODE_REVIEW.md) sets. First, [CLEANUP.md](./CLEANUP.md) finishes what the sweep after simplifying found, the one anchor index included. The longest item by far, and it needn't finish first: a later item waits only on review of the code it changes. When the review is next picked up, first consider a pass over every spec's test data (CODE_REVIEW.md, "First, when the review is next picked up").
2. **Connections folded into related entries** (below; PRODUCT.md §5.7). The rest of PRODUCT.md §5.4, Revise on a related entry, follows it, starting with one anchor index per document (below), on the two foundations they share: a related entry's relations as part of its version, and a draft whose anchor-revised documents are a list keyed by entry. That reshaping of a related entry's anchors also drops the saved quote and orphaned anchors, which nothing in the app produces once the lock is in. With them go `ResolvedAnchor`'s `status`, which leaves it `DocumentAnchor`, so `resolveAnchors` only looks anchors up; `describeAnchor`'s orphan lines and the page's italic for them; and PRODUCT.md §4.3's "quotes what it _was_ attached to".
3. **Validating content against the schema before it's stored** (below).
4. **Seed data carrying a real authoring trace**, so the history view has long, replayable sessions to be designed against. After anchor wording as marked text, since a seed's trace records whichever document shape exists.
5. **The scrubbable history view** (PRODUCT.md §5.1). Paint each frame with a read-only editor view and a `DecorationSet` built from its `FrameChange` ranges: no injected marks, no hand-built HTML. Hold frames' documents as ProseMirror nodes, not JSON (`documentsFromFrames` returns JSON today): consecutive documents share every node that didn't change, so a session's frames cost about one document plus what changed, and scrubbing either way is an index. Scrubbing across versions gives `EntryVersion` its first real reader, so make `AggregatedEntry` the current `EntryVersion` plus identity, place in the chain and relations, rather than a `version` block that repeats its `at` and `revision_id`. Explore deriving the change signals in the replay that builds frames, rather than storing them on every edit. An edit event would keep only its steps, `at` and `is_paste`, the one signal the steps don't hold, and `contentDelta`'s walks of the whole document on each keystroke would go. Comparing documents per event would be slow over a long session, so it rests on classifying steps, which anchor wording as marked text makes workable: an anchor change becomes a step whose mark type says so. Pairs with mark sets replaced by filter presets (below), which replays on every open anyway.

Further out, with no order yet: everything else in PRODUCT.md §5.

## Decided engineering work

- **Connections folded into related entries** (PRODUCT.md §5.7). Targets join `VersionedFields` as a list, and `target_id`, the `connection` relation type, `NewConnectionView` and the `new_connection` draft kind go. Once targets can change, a label stored on the row can't say what an entry is now, so annotation, update and connection derive from the current version, as §5.4 already needs for the first two; the stored kind is only related or revision. An unhighlighted connection writes nothing to either end, so what points at an entry is found only in connections' versions: the targets index covers every version, not just the current one, or a removed line vanishes from the history of the entry it pointed at. Lookups, `listDescendants`'s frontier included, fetch every connection that ever pointed in, and the fold decides which still do at the time viewed. Unifying `EntryDetailView`'s breadcrumbs was tried and dropped as not worth a two-caller helper; revisit it here, where a connection's breadcrumb becomes a related entry's plus its targets. Highlighting in a target builds on §5.4: `AnchorRef` names the entry whose document it marks (today always the parent), one `createMany` seals the connection with an anchor revision of each end that changed, and §5.4's draft outstanding against two entries becomes one outstanding against a list. The draft kinds are listed twice, in `BeginDraftInput` (`draftsStore.ts`) and `DraftOf` (`types/draft.ts`), so `new_connection` leaves both. A draft's `kind` then says only what its entry becomes, matching the stored relation, and the documents it anchor-revises sit beside it as one list keyed by entry: today's `parent`, §5.4's parent of a related entry being revised, a connection's target. What now asks `kind === 'new_related'` to mean "has a parent document" reads the list, so neither §5.4 nor a target adds a kind. `sameVersion` (`entriesStore.ts`) lists versioned fields by hand and must gain targets, or a targets-only revision is refused as no change.
- **One anchor index per document, as §5.4's first step.** The editor reads anchors in two walks, `anchorSpans` and `anchorPieces`, and anchor mode's decorations and AnchorMenu repeat them on every caret move. One `anchorIndex(doc)` returns each anchor by id (its span, its passage and wording pieces, its kind), so every caller shares one definition of where an anchor is. ProseMirror documents are immutable, so a `WeakMap` from document to index makes it one walk per new document, shared by the guard, the decorations and the commands, and a caret move walks nothing. The guard's outcome check is unchanged. §5.4's new commands (shrinking or extending an anchor, a related entry's own anchors counted as own) are built on it rather than reshaping it after. Rejected: a `DecorationSet` of sealed anchors mapped through each change. It sees text move but not marks added, so keeping it right means reading steps, which the guard exists to avoid. Further, only if a profile shows it: an index per top-level block, which an edit leaves shared, so a rebuild reads only the changed paragraph.
- **Validating content against the schema before it's stored.** `parseDocument` checks only `type === 'doc'`, and rows are immutable, so a malformed document would be permanent. Editor content is valid by construction; seeding, import, and sync won't be. The check is `schema.nodeFromJSON(json).check()`. Open question: where it lives, since the domain deliberately doesn't import the editor's schema — the store layer, or a validator injected into it. The same concern covers traces: nothing checks at runtime that a replay reproduces the entry's `content`. A step that fails ends a mark set early, and a missed step can replay silently to the wrong document. A built set should compare its last document to `content` and record whether it is complete.
- **SQLite WASM + OPFS** is the preferred long-term backend, deferred until the Dexie path has been used in anger. The composition root (`src/repositories/index.ts`) makes it a one-line swap. It doesn't change durability: OPFS is the same site storage as IndexedDB, evicted and cleared by the same rules, so persistent storage and backup answer data loss, not the engine.
- **TESTING.md's rules beyond drafts.** The draft specs follow them; the rest catch up as they're touched.
- **A revision's diff from its frames** (PRODUCT.md §5.2). Treat a whole session as one frame of the mark-set builder; `diffDocuments` (no production caller yet) is then only for a revision with no trace.

## Engineering maybes

Not decided; noted so they're not lost.

- **Automatic backup to a folder the writer picks** (File System Access; Chromium desktop only), so clearing the browser can't take the only copy, and a synced folder gives an off-device one without Chronicle touching a network. Incremental by nature, since entries never change. Elsewhere it falls back to a downloaded file. Pairs with PRODUCT.md §5.8's export.
- **A desktop shell** (Tauri, say) holding the SQLite database as an ordinary file, beside the PWA rather than replacing it.
- **A schema version on drafts and traces**, once real data must survive a schema change, so a resume or a replay knows its steps are old rather than failing on them.
- **Rebasing a stale draft** instead of refusing its save: map its steps through the intervening revision's, as ProseMirror's collab rebase does. Its trace would then start from an older version than its revision replaces, so it would have to name that version itself.
- **A related entry's own anchors as the one concept for what a session may touch.** Half-explored. Today it is "not in the base" (the guard's snapshot, `anchorsPlacedSince`), and PRODUCT.md §5.4 adds "minus the related entry's own". One rule could cover both: the entry's saved `anchors` plus those placed since the base, filtered to what's present at seal (an append-only list needs no undo tracking). The same list feeds numbering and grouping by related entry (PRODUCT.md §5.4, §6). Revisit after anchor wording as marked text and §5.4, which remove most of `anchorCommands.ts` anyway.
- **An end-to-end layer** (Playwright, whose pages in one context share IndexedDB) for what component specs fake: a real second tab, a real reload, the browser's own `pagehide`. Check Cypress's multi-tab support when this starts.
- **A Vitest Browser Mode vs Cypress write-up**, the reason every spec is mirrored. Notes so far: `.claude/skills/write-tests/mechanics.md`.
- **`documentsAt` and `buildFrames` taking a base and events rather than a `ReplayLog`**, now that a trace doesn't carry its base: the interface goes, and so does building one just to call them (`markSetsStore.ts`). Most of the cost is the replay and markFrames specs' `record` helpers, which return one, so do it when those specs are next simplified.
- **Mark sets replaced by filter presets.** A writing history is one continuous chain, and marks are only ways of cutting it, which `deriveMarks` already reads from the immutable log under any policy. So store the policy, not the frames. A writer likely settles on a few readings they like, so these would be global presets to pick between, perhaps with a per-entry choice. This is the user-facing tuning PRODUCT.md §6 ("Writing history") leaves open, and it would replace "retuning makes a new set beside the old one". Frames are then rebuilt in memory when the history opens or a filter changes. A filter re-derives rather than hiding rows: merging and deletion runs move with the policy, and each frame's `changes` are measured from the previous mark shown. That's `buildFrames`, measured at 111 ms for 31.5k events and 696 marks (AUTHORING.md, "Mark sets"). Gains: the mark-set table, repository, adapters and contract suite go, leaving three repositories, and a draft in progress plays through the same path (PRODUCT.md §6, the history view on a draft). A frame that is never stored can keep the document `buildFrames` already reaches, so a frame's `net` step, the `reproduces` check and `documentsFromFrames`, which exist to make a stored frame small and provably right, go too. Loses: opening a long history replays it rather than reading one row. A cache of built frames keyed by entry and policy, in memory or in browser storage that may be evicted freely, could hide that without being a store anything depends on. Decide before the history view is planned.
- **Formatted previews** on cards and the drafts list: the start of the document through `generateHTML` (`@tiptap/core`) and the editor's own schema, clipped by height. An `inert` container keeps its links and headings out of interaction and the accessibility tree (the card's `aria-label` names it), at the cost of find-in-page. The document CSS leaves `DocumentEditor.vue`'s scoped styles to be shared. Images are left out, or shown as thumbnails.
- **A stored `text` column, with search** (PRODUCT.md §5.5): derived at seal, as `media_refs` is, for an index to read. Drafts still flatten live, so it doesn't replace `docToPlainText`. Weigh TipTap's `generateText` against `docToPlainText` then. A hit in wording could be attributed to the related entry that proposed it, read from its `anchorWording` mark.
- **IME typing inside the session's own passage.** An input method's composition (Japanese, say, or an Android keyboard composing a word) is written by the browser at the caret and never reaches `handleTextInput`, so it isn't sent to the end of the wording: its first character stays in the passage, splitting it. Android keyboards compose ordinary words, so it may reach everyday typing there; unchecked. Fixes: move the caret to the wording's end on `compositionstart` (small, but browsers differ on honoring a selection change then), or move the composed run after `compositionend` (a second typing path). Refusing it in the guard leaves stray characters, as deferring the marker would. Neither runner drives a real IME, so either is checked by hand.
- **A revision that changes nothing, saved with its writing history** (PRODUCT.md §6, "Drafts"). One check, whether the draft recorded an event or changed a field beside the document, would decide both Save and whether a draft left unsaved is kept. It would replace `sameVersion`, whose hand-kept field list connections must otherwise extend with targets, and `sameDocument`.
